## 2. Problèmes trouvés

### A. Page « qualité des données » publique et très lente : site facile à saturer

- **Explication simple** : l'adresse `/api/v1/data/quality` est ouverte à tout le monde, sans
  connexion. À chaque appel, le serveur recalcule des contrôles sur **toute** la base (toutes
  les saisons, tous les championnats) : **7 à 9 secondes** de travail par appel, sans mémoire
  (cache) ni limite. Exemple : quelqu'un qui ouvre cette adresse 30 fois en même temps occupe
  la base de données ; les joueurs voient l'application ramer ou tomber en erreur, et le
  règlement des paris prend du retard. Cette page n'est utilisée ni par l'application ni par
  la console.
- **Gravité** : 🟠 importante
- **Où** : `backend/src/footprono/api/v1/football.py` l. 403-406 ;
  `https://footproba.duckdns.org/api/v1/data/quality`
- **Preuve** : 2 appels sans connexion : 200, 9,1 s puis 7,0 s (41 Ko). Je n'ai pas fait
  d'essai de charge (interdit), le calcul suffit.
- **Correction proposée** : réserver la page à l'administrateur (console), comme les autres
  pages d'exploitation.

```python
# football.py
from footprono.api.deps import AdminUserDep

@router.get("/data/quality")
async def data_quality(_admin: AdminUserDep, session: SessionDep) -> dict[str, Any]:
    return await run_quality_checks(session)
```

### B. Montante : deux paris possibles sur le même palier (double appui)

- **Explication simple** : quand un joueur valide le pari d'un palier, le serveur vérifie
  « ce palier n'a pas déjà un pari en cours » puis place le pari, **sans verrouiller** la
  montante. Si deux demandes arrivent en même temps (double appui sur le bouton, réseau lent
  qui renvoie la demande), les deux passent la vérification : **deux mises débitées**, et la
  montante ne suit que le second pari. Le premier devient un pari « orphelin » : il est réglé
  normalement, mais la montante l'ignore (statistiques de la montante faussées, joueur qui ne
  comprend pas pourquoi il a perdu deux mises). Argent fictif, donc pas de perte réelle.
- **Gravité** : 🟡 moyenne
- **Où** : `backend/src/footprono/bookmaker/montante.py` l. 76-80 (`_load` sans verrou),
  l. 99-131 (`place_step_bet`), l. 184-192 (`cash_out`)
- **Preuve** : lecture du code (la vérification `_open_bet` et l'enregistrement de
  `step.bet_id` ne sont protégés par aucun verrou ; le portefeuille, lui, est bien verrouillé).
  Je ne l'ai **pas** reproduit en ligne, pour ne pas créer de faux paris sur le compte de test.
- **Correction proposée** : verrouiller la ligne de la montante pendant la transaction ; la
  seconde demande attend la fin de la première, puis voit le pari en cours et est refusée.

```python
# montante.py
async def _load(
    session: AsyncSession, user: User, montante_id: int, *, lock: bool = False
) -> Montante:
    montante = await session.get(Montante, montante_id, with_for_update=lock)
    ...

# dans place_step_bet et cash_out :
montante = await _load(session, user, montante_id, lock=True)
```

### D. Inscription sans vérification du numéro (n° 5 du 12/11, toujours ouvert)

- **Explication simple** : on peut créer un compte avec le numéro de quelqu'un d'autre ; le
  vrai propriétaire ne peut plus s'inscrire, et la réinitialisation par WhatsApp repose sur ce
  numéro.
- **Gravité** : 🟡 moyenne (avant de vrais joueurs)
- **Où** : `backend/src/footprono/accounts/service.py` (`register`)
- **Preuve** : lecture du code, aucun code de confirmation.
- **Correction proposée** : code par SMS ou WhatsApp à l'inscription ; en attendant, ne
  donner un mot de passe provisoire que si le message WhatsApp vient du numéro du compte.

### E. Très grands nombres : erreur 500 au lieu d'un refus propre

- **Explication simple** : une mise de 100 milliards de milliards ou un numéro de match
  géant fait planter la requête (erreur 500, sans numéro de suivi). Aucune donnée abîmée,
  mais cela remplit les journaux d'erreurs et peut cacher de vraies pannes.
- **Gravité** : ⚪ faible
- **Où** : `bookmaker/schemas.py` l. 56 (`stake: int = Field(gt=0)` sans maximum) ;
  identifiants dans l'adresse (`/matches/{id}`, `/teams/{id}`, `/offers/main?match_ids=`)
- **Preuve** : `POST /bets` avec une mise de 10^20 → 500 ; `/matches/99999999999999999999` → 500.
- **Correction proposée** :

```python
stake: int = Field(gt=0, le=1_000_000_000)
# et pour les identifiants : match_id: Annotated[int, Path(ge=1, le=2**31 - 1)]
```

### F. Un inconnu peut bloquer la connexion d'un joueur pendant 15 minutes

- **Explication simple** : après 10 mauvais mots de passe sur un numéro, ce numéro est bloqué
  15 minutes, même pour son vrai propriétaire. Quelqu'un qui connaît votre numéro peut donc
  vous empêcher de vous connecter (en recommençant toutes les 15 minutes).
- **Gravité** : ⚪ faible
- **Où** : `api/v1/accounts.py` (connexion), `core/ratelimit`
- **Preuve** : lecture du code (le blocage est vérifié avant le mot de passe). Non essayé en
  ligne (ce serait de la force brute).
- **Correction proposée** : compter les échecs par couple « numéro + adresse » (10) et garder
  une limite par numéro plus haute (par exemple 50), ou demander un code envoyé au numéro
  après plusieurs échecs.

### G. La CI signe l'application avec la clé de développement si le secret manque

- **Explication simple** : la clé de développement et son mot de passe sont dans le dépôt
  (normal pour des essais). Si un jour les secrets GitHub de la clé de production manquent,
  la CI fabrique quand même un APK, signé avec cette clé publique, avec un simple
  avertissement. Publié par erreur, cet APK ne pourrait pas mettre à jour l'application des
  joueurs, et n'importe qui pourrait signer un faux APK « identique ».
- **Gravité** : ⚪ faible (l'APK en ligne est bien signé avec la clé de production)
- **Où** : `.github/workflows/app.yml` l. 48-50 et 101-104 ; `app/android/app/build.gradle.kts` l. 43-47
- **Preuve** : lecture du workflow ; certificat de l'APK en ligne contrôlé (clé de production).
- **Correction proposée** : faire échouer la CI au lieu d'avertir quand c'est une version à publier.

```yaml
if [ -z "$KEYSTORE_BASE64" ]; then
  echo "::error::Clé de production absente : version non publiable."
  exit 1
fi
```
